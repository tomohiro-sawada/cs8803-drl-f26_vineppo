### Goal

Validate and launch RhoMath 1.1B training using the implementation at **`9c50f14`**.

- **Skynet/A40:** LoRA GRPO, RLOO, and VinePPO. No PPO.
- **PACE-ICE/H100 or H200:** those algorithms plus PPO.
- Start with **GSM8K**, then repeat for **MATH** using its task-specific SFT checkpoint.
- Do not change segmentation rules, numerical precision, or algorithm definitions silently.

### 1. Update safely and read the documentation

Inspect local changes before pulling; do not reset or overwrite ongoing cluster work. Bring the working branch up to date with `origin/tom/work-skynet` and confirm it contains `9c50f14`.

Read:
- [`experiments/training/README.md`](cs8803-drl-f26_vineppo/experiments/training/README.md)
- **[`experiments/training/NUMERICAL_CHECKS.md`](cs8803-drl-f26_vineppo/experiments/training/NUMERICAL_CHECKS.md)**

Provision the environment **before** submitting GPU jobs:
```sh
uv sync --locked
.venv/bin/python -m pytest
```

The default environment uses HF/SDPA. Do not spend time installing vLLM or FlashAttention for this initial validation.

### 2. Locate artifacts and check storage

Resolve actual compute-node-accessible paths and export:
```sh
export GSM8K_MODEL=/absolute/path/to/gsm8k-sft-model
export GSM8K_DATA=/absolute/path/to/saved-gsm8k-dataset
export MATH_MODEL=/absolute/path/to/math-sft-model
export MATH_DATA=/absolute/path/to/saved-math-dataset
export TRAINING_CACHE=/absolute/path/to/shared-training-cache
```

These are placeholders to replace—not paths to create blindly.

Verify:
- Model revisions and dataset provenance match the intended experiments.
- Datasets are locally saved `DatasetDict`s containing `train`.
- Model/tokenizer files are complete; jobs run offline.
- Current quota and free space are sufficient.
- Cache location is outside individual run outputs.

PACE has approximately **300 GB total quota**, Skynet approximately **10 TB**. Retention keeps two checkpoints **per run**, with transient space needed for three. Checkpoints include frozen base/reference weights; they are not adapter-only files.

Create Slurm log directories before submission:
```sh
mkdir -p artifacts/training/skynet/slurm
mkdir -p artifacts/training/pace_ice/slurm
```

### 3. Complete the GPU numerical acceptance checks

Use an allocated GPU—not the login node—and follow `NUMERICAL_CHECKS.md`.

Before a long run, demonstrate:
1. Zero-initialized LoRA agrees with the starting reference on fixed inputs.
2. Old/new policy ratios are near one before updates.
3. Only FP32 actor adapters enter the optimizer; base/reference weights remain unchanged.
4. Nonconstant-reward batches produce finite gradients and actual adapter updates.
5. FP32 and BF16-base comparisons use **identical fixed data**, not independently sampled trajectories.
6. Microbatch splitting preserves the logical update within justified tolerances.
7. Checkpoint/restart reproduces fixed-input scores and optimizer state.
8. GRPO/RLOO tied groups produce zero policy advantages; neither invokes MC sampling.
9. Memory fits after optimizer initialization and at representative sequence lengths.

Implement a small diagnostic harness if necessary. The benchmark logs alone do not prove all these properties.

For **VinePPO**, also validate actual RhoMath-generated token IDs against the strict segmenter. OpenRouter proxy results do not establish sampled-token compatibility. Report any rejection without silently snapping boundaries, skipping samples, or substituting a fallback.

### 4. Benchmark before choosing the run length

After numerical validation, submit a small LoRA benchmark. Example for Skynet:

```sh
sbatch experiments/training/skynet/benchmark.slurm \
  --algorithm grpo --finetuning lora --dtype bfloat16 \
  --lora-rank 16 --lora-alpha 32 --learning-rate 1e-5 \
  --num-samples 4 --num-iterations 5 --warmup-iterations 1 \
  --task gsm8k \
  --model-path "$GSM8K_MODEL" --dataset-path "$GSM8K_DATA" \
  --output artifacts/training/skynet/gsm8k-grpo-lora-bench-01
```

Use separate output directories for `rloo` and `vineppo`. For VinePPO, specify the intended MC count, such as `--mc-num-samples 4`.

On PACE:
- Use `experiments/training/pace_ice/benchmark.slurm`.
- Put `--constraint=gpu-h100` **before** the script.
- Pass `--expected-gpu H100` **after** it.
- For H200, change both values consistently.

Inspect `metadata.json`, `metrics.jsonl`, and `summary.json`. Report measured iteration time, phase breakdown, token counts, memory peaks, and checkpoint size/time. Five iterations remain a pilot, not a reliable whole-run forecast.

### 5. Launch a training pilot after the gates pass

For example, on Skynet:

```sh
sbatch experiments/training/skynet/train.slurm \
  --algorithm grpo --finetuning lora --dtype bfloat16 \
  --lora-rank 16 --lora-alpha 32 --learning-rate 1e-5 \
  --num-samples 4 --num-iterations 100 \
  --checkpoint-every 10 --keep-checkpoints 2 \
  --task gsm8k \
  --model-path "$GSM8K_MODEL" --dataset-path "$GSM8K_DATA" \
  --output artifacts/training/skynet/gsm8k-grpo-lora-pilot-01
```

Use this configuration only if its precision and memory checks passed. Adjust requested walltime within the cluster’s allowed QoS based on measurements. **100 iterations is a pilot, not an established convergence budget.**

Repeat with distinct outputs for other algorithms/tasks. PPO belongs on PACE; its critic remains full-parameter even with actor LoRA.

The runner does not automatically perform held-out evaluation. Evaluate before and after the pilot using a fixed protocol before expanding the budget.

### 6. Report back

Return:
- Commit, cluster, GPU, job IDs, exact commands, and output paths.
- Numerical checks passed/failed with observed errors and tolerances.
- Segmentation findings for VinePPO.
- Throughput, memory, checkpoint storage, and any failures.
- Before/after held-out results when available.
- Recommended next budget and LR/rank experiments.

Do not claim learning success merely because training completed. Preserve failure evidence and stop rather than silently changing the experiment.
